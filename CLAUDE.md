# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Working rules

**Git: never commit.** Only the user commits. Read-only git commands (`status`, `diff`, `log`, `show`, `blame`, …) are always fine. Never run anything that rewrites history (`rebase`, `reset --hard`, `commit --amend`, `push --force`, `filter-branch`) unless the user explicitly asks for that specific operation. Leave changes staged/unstaged in the working tree and say what you changed.

**READMEs are for humans.** The root `README.md` and each package's `README.md` hold operational instructions for people — how to install, run, deploy, add a token, etc. Keep them current as you change things, and keep them **very brief and direct**: commands and steps, no prose, no background essays. Architectural context and agent-facing guidance belongs here in `CLAUDE.md`, not in the READMEs.

**Follow `specs/` for all client code.** [`specs/CODING_STYLE.md`](./specs/CODING_STYLE.md) and [`specs/NEXTJS_DATA_FLOW.md`](./specs/NEXTJS_DATA_FLOW.md) are binding, not advisory — read them before writing anything under `client/`. They were ported from `/Users/roger/Dev/CC/ec-dapp/specs/` (the upstream reference implementation); read the originals when a rule needs context, and keep the ports in sync when upstream changes. Deliberate differences are marked **[diverges]** in our copies — don't "fix" those back.

**Starknet only — ec-dapp gives us style, not its chain.** ec-dapp is an Ethereum/EVM app; we import its coding style and data-flow conventions and nothing else. This project's chain is **Starknet** (Cairo/Dojo, `@starknet-react/core`, Cartridge Controller, Torii). Never bring an EVM library, address type or ABI convention across from it.

## Client (`client/`)

Next.js 16 (App Router, Turbopack), React 19, TypeScript, Tailwind 4, at `http://localhost:3000/`. **`specs/CODING_STYLE.md` and `specs/NEXTJS_DATA_FLOW.md` govern everything here.** Layout:

```
client/
  .storybook/     main.ts + preview.tsx — the ui/ preview surface
client/src/
  app/            ONLY what Next.js requires: layout.tsx, page.tsx, api/, actions/
  components/     everything else — generic components, providers/, ui/ (cva primitives
                  + a *.stories.tsx next to each)
  components/pages/<page>/  one folder per page: its page component + its own parts
  dojo/           chain profiles: profiles.ts (the table), config.ts (PROFILE), torii.ts
  hooks/          use-controller.ts (chain), use-card-art.ts + use-pose-animation.ts (the table), plus:
  hooks/queries/  one react-query hook per API query route
  hooks/mutations/ one hook per server action, over useActionMutation
  lib/            cn(), client-utils (handleApiError), card-geometry / card-art / card-pose (3D cards)
  stores/         settings-store.ts — zustand, the persisted player settings
  styles/main.css the ONE stylesheet: Tailwind import + @theme tokens + base elements
```

- **`app/` is routing only** (`specs/CODING_STYLE.md` § File layout). `app/page.tsx` is a mount point — `return <HomePage />` — and every route's markup, state and providers live in `components/`. `Providers` is `components/providers/providers.tsx`, not `app/providers.tsx`. Applies to all new UI: component first, route grows an import.
- **A page is a folder: `components/pages/<page>/`.** The `/` route is `components/pages/home/HomePage.tsx`, `/collection` is `pages/collection/CollectionPage.tsx`, `/collection/<slug>` is that folder's `ContractPage.tsx`, and anything written *for one page only* lives beside it — including a `layout.tsx`'s component (`pages/collection/CollectionScene.tsx`), which is a page-folder citizen like the rest. Only genuinely generic pieces — `Header`, `ControllerButton`, `NavigationCard`, `TokensPanel`, `ElapsedTimeBadge`, `ui/` primitives — sit at the top of `components/`; a page-local component graduates there the day a second page needs it, not before.
- **`Header` is mounted once, in `app/layout.tsx`** — logo home-link left, `ControllerButton` right. The layout wraps it and `children` in a `flex min-h-screen flex-col` div, so **every page's `<main>` uses `flex-1`, never `min-h-screen`** (that would add the header's height to the viewport and produce a scrollbar on every page).
- **Tailwind 4, no other CSS.** Tokens are the `--color-ps-*` set in `main.css`'s `@theme` (→ `bg-ps-bg`, `text-ps-bold`, `text-ps-accent`, `border-ps-line`). Compose classes with `cn()`. Tailwind is wired through `postcss.config.mjs` (`@tailwindcss/postcss`) — there is no `tailwind.config.*`, v4 configures in CSS.
  - Shadows are tokens too — `--shadow-vignette` (the viewport rail) and `--shadow-card` / `--shadow-card-hover` (panels lifted off the felt, used by `NavigationCard`). Reach for `shadow-card`, don't hand-roll a `shadow-[…]`.
  - The palette has **three knobs** — `--color-ps-bg` (the felt), `--color-ps-text` (white), `--color-ps-accent` (yellow); `panel`/`line`/`bold` are `color-mix()`-derived from them, so re-tinting the table is a one-line edit. Never write a literal colour in a component.
  - **The felt is switchable, and that is the whole mechanism for a themed surface.** `--ps-table-green` / `-red` / `-blue` are the casino-carpet tones in `@theme`; `--color-ps-bg` defaults to red and `html[data-table='green' | 'blue']` in `@layer base` re-points it (the default felt is the one with no block — change the default and the blocks change with it, in `main.css` and in `TABLE_COLORS`, which leads with it). Because `panel`/`line` are `color-mix()`es of `--color-ps-bg` *declared on the same element*, they resolve against the override and every panel, border, shadow and stamp moves with the felt — nothing else in the app knows a table colour exists. `SettingsProvider` sets the attribute from `tableColor` in the settings store; a fourth table is a tone plus a two-line block. Verified in a production build: Tailwind keeps both the tones and the attribute blocks.
  - **Base element styles live inside `@layer base`.** Outside a layer they beat every utility by source order, so `<h3 className="text-ps-accent">` would silently do nothing.
  - **The table surface is three fixed pseudo-elements**, all `pointer-events-none`, all tuned by `--ps-stamp-*` / `--shadow-vignette` tokens: `html::before` (bevel highlight) and `body::before` (the logo stamp) at `-z-10`, `body::after` (viewport vignette) at `z-50`. Two non-obvious constraints hold this together — **the felt colour is on `html` only**, because a background on `body` paints *above* body's negative-z children and would bury the stamp; and the bevel is a masked second element rather than a `drop-shadow`, because filters are applied *before* masking, i.e. to the flat rectangle.
  - **The bevel is only the lip**, not a full offset copy of the stamp — an offset lattice with the stamp subtracted out (`mask-composite: intersect, subtract, add`), leaving a crescent. A whole copy underneath cancels light against dark across the entire silhouette, so the stamp stops darkening the felt and the texture reads *brighter* — the opposite of a stamp. The offset lattice layer is shifted along with the copy so the crescent is never clipped at a cell boundary.
  - **The stamp lattice is masks, not a tile asset.** CSS tiling has no spacing — the drawn size *is* the repeat period — so `body::before` tiles `logo_mask_b.png` edge to edge as a mask and intersects it (`mask-composite: intersect`) with a `conic-gradient` checkerboard of twice the period. What survives is the brick lattice: rows one logo apart, every other row shifted 50%. The logo is a solid silhouette, so masking a flat colour reproduces it and leaves the stamp re-colourable.
- **Fonts are self-hosted from `client/public/fonts/`**, declared in `client/src/styles/fonts.css` — `@font-face` and nothing else, `@import`ed at the top of `main.css`. It is the *one* sanctioned exception to the one-stylesheet rule (marked **[diverges]** in `specs/CODING_STYLE.md`), justified only by being generated boilerplate that decides nothing; family names and sizes stay in `@theme`. **Two type roles, named for the role rather than the face** — `--font-title` (headings and buttons, always paired with the `small-caps` utility, which exists because Tailwind has no `font-variant-caps`) and `--font-mono` (body copy; it's the `<body>` default, so nothing asks for it). No component ever names a family, so re-facing the game is a one-line `@theme` edit; `--font-title`, not `--title-font`, because Tailwind's `--font-*` namespace is what generates `font-title`. The files are copied from `/Users/roger/Dev/Realms/pistols/client/public/fonts/` (whose `styles/fonts.scss` is the reference for the `@font-face` blocks): **EB Garamond** (variable TTF, roman + italic) → `--font-title`; **Courier Prime** (8 woff2 subsets) → `--font-mono`. `font-display: block` on all of them — these are display faces, a swap flash is worse than a beat of invisible text. Pistols also ships Xanh Mono and Pinyon Script; both are unreferenced there, so they were not copied.
- **Every component accepts an optional `className`**, merged last through `cn()` onto its root element (`specs/CODING_STYLE.md` § Styling). Applies to page-level and feature components too, not just `ui/` primitives.
- **Icons: `lucide-react` only**, sized/colored with Tailwind utilities. Game art is not an icon — that goes in `public/assets/`.
- **`ui/` primitives use cva, and the variant axes are named the same everywhere**: `variant` = `primary` (default) / `secondary` / `ghost` / `text`, `size` = `sm` / `md` (default) / `lg`. `Button` is the reference — `primary` is the header's Connect button, `secondary` the quieter panel-coloured sibling, `ghost` an icon-only control whose whole hover state is the accent, `text` the header's account name (no box at all). Never invent `type`/`kind`/`color` for the same axes on another primitive (`specs/CODING_STYLE.md` § Component styling API).
  - **Feedback is motion, not fading**: `not-disabled:hover:scale-105` + `not-disabled:active:scale-95` at half the duration. **`opacity` means disabled** — no variant dims on hover. `text` opts out of both (it has no box to swell) and rides 90% → 100% instead.
  - **Every interactive state is gated behind `not-disabled:`.** An un-gated `hover:border-ps-accent` still lights up on a disabled button and cancels the `disabled:opacity-50` signal — this was a real bug, don't reintroduce it.
- **Storybook** (`@storybook/nextjs-vite`, config in `client/.storybook/`) is the wallet-free preview surface for `components/ui/`. `pnpm storybook` (:6006), `pnpm dev:all` (dev + Storybook), `pnpm build-storybook` (→ `client/storybook-static/`, gitignored). Rules are in `specs/CODING_STYLE.md` § Storybook; the two that get broken most:
  - **One story shows all variants together.** Each primitive gets `All` (the whole matrix on one page, grouped by axis) plus a controls-driven `Playground` — not `Primary`/`Secondary`/`Large`/`Disabled` as separate stories. Adding a variant means extending `All` in the same change.
  - **`variant`/`size` need explicit `argTypes`** (`control: 'select'`). cva's `VariantProps` is type-level only, so react-docgen can't see it and the Playground silently loses those controls.
  - `preview.tsx` imports `main.css` and nothing else — the felt, stamp and vignette are on `<html>`/`<body>`, so the preview iframe gets the real surface for free. No background decorator. `staticDirs: ['../public']` is required (unlike `next dev`, the builder doesn't serve `public/`, and `main.css` reaches into it for the fonts and the stamp).
- **Data flow**: API query routes + react-query hooks for reads, server actions + `useActionMutation` for writes. No `useEffect` fetching. The chain layer is used bare — never wrapped in another query layer.
- **Client state is zustand, in `src/stores/`** — `settings-store.ts` (`useSettingsStore`) is the first one, ported from ec-dapp's `src/stores/settings-store.ts`. Rules in `specs/CODING_STYLE.md` § Client state; the load-bearing ones:
  - **Every field in the settings store is persisted** — it holds durable player preferences only, so `persist` runs with no `partialize` and a new setting costs a field plus a setter. Session UI state (open panels, in-flight flags) gets its own unpersisted store; server data is react-query's, never a store.

That is also where every future persisted store rehydrates. ## The 3D card table (`client/src/components/pages/collection/` + `lib/card-*`)

`/collection` is a **three.js table**: every ERC-721 collection is a face-down deck on the felt, picking one deals a page of its cards face up, and picking a card brings it to the camera instead of opening a modal. The same components serve the full game collections later — a deck is a contract plus a list of token ids, so a collection nobody owns is the same code fed a different list.

- **Which deck is open is the URL, and the table is mounted by the *layout* because of it.** A deck is `/collection/<slug>` (`contracts.json`'s `slug`, carried through `PROFILE.tokens`), so `/collection` and `/collection/karat2` are sibling route segments — Next unmounts one page component to mount the other, and a `<Canvas>` that unmounts loses its WebGL context and every animation this table is built on (decks would appear already swept aside, the camera already pulled back, closing a deck would be a cut). So `app/collection/layout.tsx` mounts `CollectionScene`, which owns the `CardTable` and the view state, and the two pages are **only the chrome over it**: `CollectionPage` (the deck list's heading) and `ContractPage` (the open deck's title and paging), reading the scene back through `useCollectionView()`. Verified in the browser: navigating between the two routes keeps the *same* canvas DOM node, in both directions and through browser Back/Forward.
  - **The scene reads the slug itself, with `useSelectedLayoutSegment()`** — the layout is above `[slug]`, so that hook is what sees it (null on `/collection`). `CardTable` still takes an index, because it lays decks out by position; the scene maps slug → index and `onSelect` is a `router.push`. Escape and the back button are the same navigation, which is why the browser's own Back button works.
  - Page and zoom are the only state left, and they are deliberately **not** in the URL — nobody links to page 3 of a deck. They reset on a `slug` change rather than in the click handler, so Back and Forward reset them too.
  - `app/collection/[slug]/page.tsx` **404s a slug no collection answers to** (`notFound()`), instead of leaving an empty table at a working URL, and `generateStaticParams` prerenders all eight — the list is a compile-time constant.
- **react-three-fiber, not imperative three.js.** The scene is React components (`CardTable` → `Deck3D` / `Card3D`), so a card is props and state like anything else, and R3F disposes what it mounted. `@react-three/drei` is in for `<Html>` and `useCursor` only. `/Users/roger/Dev/Realms/pistols/client/src/three/` (`CardMesh.tsx`, `InteractibleScene.tsx`) is the imperative prior art — read it for reference, don't copy the pattern: most of that file is tween bookkeeping this layer doesn't need. **CSS 3D transforms were the alternative** and were rejected: no thickness, no lighting, no shadows, and paint-order sorting instead of a depth buffer.
- **The canvas is transparent and paints nothing of its own.** The felt, the logo stamp and the vignette stay CSS (`styles/main.css`), so switching the table colour in the burger menu re-tints the felt *under* a live 3D scene and the scene never learns a colour exists. The only non-card geometry is a `shadowMaterial` plane at y=0 that draws the cards' shadows onto whatever the page shows through. `<Canvas flat>` — ACES tone mapping would quietly desaturate every token's art.
- **One geometry for every card, built procedurally** (`lib/card-geometry.ts`): a rounded rect extruded to a thickness, then re-cut into three material groups. `ExtrudeGeometry` emits *both* caps in one group and the side walls in another, so the front and back would share a material — `buildCardGeometry` splits the caps in half (front/back decided by vertex z, not by three's ordering) and normalizes the extrusion's raw-coordinate UVs over the card box. **The back's V is inverted, i.e. its art is printed upside down relative to the front**, and that is required rather than cosmetic: the back is seen from the other side (one mirror) *and* the card has been turned end over end about its horizontal axis to show it (a second mirror), which leaves the art unmirrored but upside down. Inverting V cancels it, so a card reads upright both ways up and the flip stays a single-number sweep.
- **Poses in, animation out.** `lib/card-pose.ts` defines a `Pose` (position + `YXZ` Euler + scale); `table-layout.ts` derives every pose as a pure function of the view; `hooks/use-pose-animation.ts` damps each object toward its target every frame, outside React (a card crossing the table costs zero renders). **No tween library, deliberately** — a deck can be opened, paged and closed faster than a deal finishes, and a damped target absorbs interruption for free. Two consequences worth knowing: the **flip is one number** (sweeping the tilt from `FACE_DOWN` to `FACE_UP` passes through upright, so the card stands up, turns to the player and lies down), and the **deal arcs** because the lift is derived from the distance still to travel, so it falls to zero on arrival by itself. `YXZ` order is load-bearing: in the default `XYZ` the spin rides on the tilt and a flip corkscrews.
- **`table-layout.ts`'s `TABLE` object is the one place the table is dimensioned** — grid columns/rows, gaps, card scale, deck stack, camera angle/fov, zoom fill, hover lift. Every function reads it at call time, so a number there is the whole edit; **to fit more cards, raise the grid counts and/or take `cardScale` below 1**. Nothing is in pixels: `FitCamera` keeps the camera's angle and backs it off until the layout fits the viewport, so changing the grid re-frames the shot on its own.
  - **Every angle in `TABLE` is in degrees, and that is a rule for anything added to it** — these are numbers a person sets by eye, and `6` reads as an angle where `0.105` reads as nothing. The file's `radians()` is the only crossing: `Pose.rotation`, `FACE_UP`/`FACE_DOWN` and everything three.js takes stay radians, so a `TABLE` angle is never used raw. `direction` is exempt because it is a vector, not an angle, and `fov` passes straight through (three.js wants degrees too).
  - **Dealt cards lie flat: `gridTilt` is 0.** The camera is steep enough (`direction`) that a flat card still reads, and because cards are lit and shadowed, leaning one back toward the camera looks like a *bent* card rather than a raised one. The knob is kept, not removed, and `gridPose` lifts a leaning card back out of the felt on its own, so it is safe to turn up again. Hover is what raises a card — that is `hoverLift`/`hoverTilt`, and it is deliberately the only thing that does.
  - **The zoomed card is framed around the card *and* its caption, on both axes.** `zoomFill` is a fraction of the whole assembly, not of the card: fitting the card to a fraction of the viewport *height* alone overflows a portrait window sideways, and ignoring the caption hangs it off the bottom edge (both were real bugs). `zoomCaptionDrop`/`-Height`/`-Width` are the caption's box in card units, `CardTable` positions the `<Html>` from `zoomCaptionDrop` so the two cannot drift, and `CAPTION_SCALE` there is what relates its Tailwind pixel sizes to card units (drei's `<Html transform>` maps 1px to `scale * 10/400` units of its parent's space). They estimate a DOM box, so keep them generous. Verified by projecting all eight corners to NDC across aspect 0.5–2.2: max |ndc| is exactly `zoomFill`.
- **Card art is rasterized, cached and disposed** (`lib/card-art.ts` + `hooks/use-card-art.ts`). Torii serves the Pistols tokens as a **~750KB SVG** (viewBox 771×1080, artwork embedded as base64) and `card_back.png` is 2996×4197 — neither can go to `TextureLoader`, so both are drawn into a card-shaped canvas at `CARD_ART_HEIGHT` and uploaded as a `CanvasTexture` (`drawImage` with explicit dimensions is what rasterizes an SVG at a chosen resolution). Drawing also letterboxes art of a different aspect onto card stock instead of stretching it. The cache is an **LRU with a hard cap** — the test account holds 544 Duels, and paging a deck end to end would otherwise upload gigabytes and never let go. **This is the one fetch not on react-query**, because a texture needs disposing on eviction and a query cache cannot do that (`specs/NEXTJS_DATA_FLOW.md` §1 prohibits `useEffect` for *app data*, not for loading images).
- **Torii's image endpoint serves corrupt files, and every card fetch has to be validated and retried.** `/static/<contract>/<token>/image` rebuilds the file on *every* request — the SVG branch of `torii/crates/server/src/artifacts.rs` never writes the `image.hash` that `check_image_hash` reads, so `should_fetch` is always true — and then serves it by `File::create` (truncating) → `write_all` → reopen and read back, with **no flush and no lock**. The read races the write it just issued, and the loser gets **HTTP 200 with an empty or short body**. That is not an error an `<img>` can see: `onerror` fires for an empty body but a truncated SVG parses and draws blank, which is why some cards were blank with nothing in the console. So `card-art.ts` fetches the bytes itself, **rejects an empty body or an SVG with no closing tag, and asks again**; a blob URL then feeds the `Image` (which also retires `crossOrigin` and any chance of a tainted canvas).
  - **The retry must bypass the HTTP cache (`cache: 'reload'`), and that is the load-bearing half.** Torii serves the image `cache-control: public, max-age=3600`, so the browser caches the empty body **as a successful response** and replays the identical 0-byte answer to every later request for that url, for an hour, across reloads — a retry that reuses the cache is not a retry. A/B in Chrome over 20 cold ids, same loop otherwise: **1/20 loaded reusing the cache, 20/20 bypassing it**. `reload` also *replaces* the poisoned entry, so it heals the url for everything that asks later.
  - **Beware of measuring this endpoint from node** — `node:fetch` has no HTTP cache, so the bug above is invisible there and a broken fix measures perfect (it did). Verify card art in the browser.
  - **Do not "fix" this by throttling.** Measured against the live mainnet indexer, dealing a page of twenty: ~36 requests total (≈1.8 per card) and that count is **flat in the concurrency**, while wall time goes 13.5s at one-at-a-time → ~4s at six. Serializing buys the indexer nothing and costs the player ten seconds. `ART_CONCURRENCY` is only a burst cap so a 500-card collection doesn't open 500 sockets.
  - The Duelist tokens' `image` is an **`https://assets.underware.gg/...` URL, not a data URI** (checked over all 7058 indexed rows), so each of those Torii requests re-fetches from that origin too — one more reason the endpoint is slow and racy, and the reason a cached-empty response is so likely on a cold page.
  - **4xx is never retried.** A token id past the collection's supply 404s honestly (verified on mainnet), and retrying it burns every attempt to reach the same answer — hence `PermanentArtError`.
- **The letterbox is the collection's own colour, and `Card3D`'s `background` prop is the one knob.** A square token (Karat is 960×1200) leaves ~55px of stock top and bottom on a 5:7 face, and filling that with cream paper reads as a stamp on the wrong card — so `background` comes from `useContractMeta(address)?.backgroundColor` (the collection's own colour, else `contracts.json`'s `bgColor`) and defaults to `CARD_PAPER_COLOR`. Two things make it hold together: **`background` is part of the art cache key** (`url@height@background`), because two collections can legitimately want the same image on different stock and must not share an entry; and the **blank face uses the same colour as the letterbox**, so a card doesn't paint cream and then turn dark when its texture lands. The **rim stays paper** on purpose — art is printed on stock, and the edge is where the stock shows. Per-token `background_color` also exists in token metadata (Duel tokens declare `000000`) and would override the contract's, but nothing fetches token metadata yet.
- **Browsing deals art up, all at once** — a collection is there to be read, so a card is never held back waiting for its texture; it deals as blank stock and the art appears on it when it lands. **The flip is kept, unused, as `Card3D`'s `faceDown` prop**: it selects `faceDownPose` (the same slot, back up), and since poses are damped toward, passing it *is* the turn-over animation. That is for the game — a hand dealt face down, cards turned over one at a time — and `faceDown={!loaded}` is the one-line way back to a per-card reveal. Hover is the only thing `Card3D` decides for itself; where a card goes and which way up is always a prop.
- **Big decks are paged, not dealt.** `gridPageSize()` cards are on the felt at a time and the deck parks beside the grid as the pile; a deck's stack is drawn as `TABLE.deckStack` cards whatever the real count, because a deck reads as a deck at nine and never at five hundred.
- **A deck with nothing left in it draws the empty slot** — a dashed card-shaped outline (`lib/card-placeholder.ts`), for a collection nobody owns *and* for an open deck whose last page is out on the felt. `Deck3D` decides on `remaining` (the pile), never on `count` (the collection, which still labels the deck). **The open deck is a pile you deal from**: clicking it with cards left in it deals the next page (`onTurnPage`, the same call the page chrome makes), and clicking it emptied puts the deck back — it is the space the cards came out of, so it closes the deck the way Escape and Back do, animation and all. A collection with no cards at all is inert. Which of the two a deck is, is `CardTable`'s call: it hands `Deck3D` a handler or none, and no handler means no cursor and no hover lift either. **The slot never animates — it is part of the table**, a marking on the felt saying where cards go, so it is a plainly placed group while only the stack (`DeckStack`) gets the damped one; hover lights its label but moves nothing, and a swept deck leaves no marking behind. Keeping the two as separate components is also what stops a stack that comes *back* (paging back onto a pile) from flying in from the table's centre — it mounts fresh, and `usePoseAnimation` places an object the frame it mounts. Consequence worth knowing: a deck that fits in one page has an empty pile the instant it opens, so it swaps to the slot rather than sliding to the parked spot.
  It is drawn at **95% of a card and as low as the shadow catcher allows**, so any card in that place covers it completely — at full size its dashes graze the card's own edge and read as a halo rather than as an empty space. It is a **canvas texture on a plane in the scene**, for two reasons: an `<Html>` div has no depth sorting and would paint over every card that crosses the pile — including the zoomed card, which fills the frame — and WebGL clamps line width to 1px, so a line loop cannot be a thick border. A canvas has `lineWidth` + `setLineDash` + `roundRect`, i.e. the same knobs the CSS version would use.
- **Cards return to their deck's cell, not to the pile** (`deckTopPose`). The deck is already sliding home when they set off, so aiming them at the parked spot landed them next to nothing and blinked them out; the target is the top of that deck's *drawn* stack, so a three-card deck catches them three cards up. `dealt` outlives `selected` by exactly `RETURN_MS`, which is what keeps a deck under them the whole way.
- **HTML over the cards, two ways, and they are not interchangeable.** Screen-space `<Html>` (deck labels) projects a 3D anchor and positions a plain div — crisp text, Tailwind classes, cheap. `<Html transform>` (the zoomed card's caption) renders the div *in* the scene so it inherits the card's tilt, travel and scale and reads as printed on it — one DOM subtree per instance and no depth sorting against meshes, so it is for the one card in the player's hands while the twenty on the felt stay pure texture. Page chrome that needs neither (title, paging, Escape) is ordinary DOM over the canvas, `pointer-events-none` with each control turning its own back on.
- **A card in hand steps along the row: ← / → and a chevron each side.** `stepZoom(delta)` in `CollectionScene` moves the zoom through `hand` — the dealt page, in table order — so one card goes down as the next comes up, which is free: both poses are derived from `zoomed` and damped. It is **bounded by the page** (it stops at either end instead of wrapping or paging) because the cards on the felt are the ones that can be picked up; `ContractPage`'s chevrons grey out there. The keys live with Escape in the scene, since they are global, and are taken **only while a card is zoomed** — with nothing in hand the arrows belong to the page.
- **The zoom dimmer is a plane in the scene**, not a div over the canvas: it has to sit *between* the zoomed card and the rest of the table, and a DOM overlay can only be in front of the whole canvas or behind it. It stays mounted with a damped opacity and takes an `onClick` only while active — R3F leaves objects with no handler out of hit testing entirely, so an inert backdrop can't swallow hovers on the cards behind it.
- **Cards cast shadows but don't receive them** — they sit nearly coplanar and self-shadowing at that angle is all acne and no shadow.
- **Testing this page needs a foreground tab.** A backgrounded or non-selected tab gets no `requestAnimationFrame`, so R3F's loop never runs, nothing renders *and* `<Html>` never gets positioned (it projects in `useFrame`). The symptom is a blank canvas with the labels stacked below the fold — check `document.visibilityState` before debugging the scene.

## Chain profiles (`client/src/dojo/`)

One network at a time, selected by profile — **ported from `/Users/roger/Dev/Realms/LORE/packages/client-sn/src/dojo/`**, which is the reference for this layer. Read those files when a rule here needs context.

- **`profiles.ts`** — the profile table. Only `mainnet` and `sepolia` exist (LORE also has a local Katana; we don't). Each profile carries `chain` / `chainName` / `rpcUrl` / `toriiUrl` / `manifest` / `namespace`, and `getProfileConfig()` derives `chainId`, `contractAddresses` and `tokens` from it. **A profile holds a single `manifest`** — LORE splits every field into `{ starknet, appchain }` because it bridges to an appchain; there is no appchain here, so never reintroduce that shape.
- **`config.ts`** — `PROFILE`, the active profile, plus `PROFILE_NAME`. **Everything chain-dependent imports `PROFILE`; nothing else reads `process.env` for chain config.** `NEXT_PUBLIC_PROFILE` picks the network (default `mainnet`), `NEXT_PUBLIC_RPC_URL` / `NEXT_PUBLIC_TORII_URL` override one URL each. Every var and its default is in `client/.env.example`; `torii/.env.example` covers the indexer.
- **`torii.ts`** — `getToriiClient()`, one lazily-created `ToriiClient`. The **dynamic `import()` is load-bearing, keep it inside the factory** (and the `ToriiClient` type import `type`-only): `@dojoengine/torii-client` re-exports `@dojoengine/torii-wasm`, whose module body instantiates a **2.7MB WASM binary at import time**. A static import puts it in the initial page chunk and every visitor downloads it before connecting — measured both ways, `…dojo_wasm_bg….wasm` is requested on first paint with a static import and not at all with the dynamic one. (It is *not* about SSR: a static import still builds and `/` still prerenders static.)

### Contract addresses — two sources, never hand-typed

`PROFILE.contractAddresses` is keyed by **game**, and `PROFILE.tokens` is the flat list of every ERC-20/ERC-721 across games. Neither is ever hand-typed, and there is **no hardcoded list of token names** — that drifts.

- **Which contracts are tokens, of which type, for which game** — all from **`contracts.json` at the repo root** (imported via the `@root/*` tsconfig alias), filtered to `enabled: true`. That is the same file the Torii indexer reads, so `PROFILE.tokens` is exactly what Torii has balances for. Adding a game's tokens = edit `contracts.json`, redeploy the indexer. Anything `enabled: false` (`realms/lords`, the `world` entries) never reaches the client.
  - Each entry's **`slug` is a URL-facing id** — it is the collection's name in `/collection/<slug>`, so it is unique per network and **renaming one breaks any link to that deck**. `name` stays the human label on the felt (`Karat G2`), `slug` the route (`karat2`).
- **Addresses** — for the `pistols` game from the Dojo manifests in **`@underware/pistols-sdk`** (`/pistols/config` getters), which stay authoritative for the world's own deployments; for every other game from `contracts.json`, which is the only place they exist.
- `contractAddresses.pistols` additionally holds the **game contracts** (world, game, game_loop, bank, admin, vrf, …) from the manifest — they are an address registry, not tokens, so they are never queried for balances. Addresses a network never deployed resolve to `0x0` and are dropped.
- `pistols/lords` is a deliberate loose end: the manifest resolves it (so it is in `contractAddresses.pistols`) but `contracts.json` lists LORDS under the disabled `realms` game, so it is **not** in `PROFILE.tokens` and no balance is shown. Left for later on purpose — don't "fix" it by hardcoding it back in.

### Providers (`client/src/components/providers/`)

Connected through the **Cartridge Controller**; connector versions match `/Users/roger/Dev/Dojo/controller/examples/minimal` (`starknet` 8, `@starknet-react/*` 5, latest `0.13.x` Controller). All versions in the root `catalog:`.

- `StarknetProvider.tsx` — the `ControllerConnector` is built **once at module scope** (it reuses `window.starknet_controller` and warns if constructed twice), from `PROFILE`: `chains`, `defaultChainId`, `namespace`, `toriiUrl`. Every `window` access inside the controller is guarded, so this module SSRs fine — no `dynamic(…, { ssr: false })` needed, and `/` still prerenders static.
- `providers.tsx` — `Providers`: creates the one `QueryClient` and hands it to `StarknetConfig`, which mounts the `QueryClientProvider` itself. One provider, one cache, shared with the app's own queries (`specs/NEXTJS_DATA_FLOW.md` §0). Wraps children in `TokensProvider`.
- `TokensProvider.tsx` — cloned from LORE's `tokens-provider.tsx`, widened from its single ERC-721 to every contract in `PROFILE.tokens`. **The app's one Torii subscription**: it pages `getTokenBalances` for the connected account, then streams `onTokenBalanceUpdated`. Components read it through `useTokenBalances()` / `useCoinBalance(game, name)` / `useTokenIds(game, name)` — never a second query layer over it. Torii leaves `token_id` unset for ERC-20s; that is what splits `balances.erc20` from `balances.erc721`.
- `ContractsProvider.tsx` — every token contract's **collection metadata**, read once from `getTokenContracts` and served by `useContractMeta(address)` as `{name, symbol, description, externalLink, image, backgroundColor}`. This is the contract's own metadata (Torii's `token_id IS NULL` row), i.e. what the contract URI says about the *collection* — not per-token traits, which are a different call (see below).
  - **A provider, not a store, and not react-query.** It is server data, and `specs/CODING_STYLE.md` § Client state reserves stores for client state — nothing in here is a player decision. It is not react-query for the same reason `TokensProvider` isn't (the chain layer is used bare, `NEXTJS_DATA_FLOW.md` §0), and because the one thing it *does* want — surviving a reload — is a dozen lines of `localStorage` versus persisting a `QueryClient` shared with every starknet-react connector query.
  - **Separate from `TokensProvider`, mounted outside it.** This data is account-independent and that provider's effect is keyed on `address`, so folding it in would re-fetch every collection on each connect and disconnect. There is also nothing to subscribe to: a collection's metadata is written once, at deploy.
  - **Cached in `localStorage` under `ps.contracts.<profile>.v1`**, keyed by profile *and* by the sorted address set, so adding a contract to `contracts.json` invalidates it on its own; a 24h TTL is the only other escape hatch (the content really doesn't change, but a collection that ships a metadata fix shouldn't be wrong forever). Verified: a reload issues `RetrieveTokenBalances` and no `RetrieveTokenContracts`. Read in the mount effect, not a `useState` initializer — same hydration reason persisted stores use `skipHydration`.
  - **Data-URI images are stripped before caching.** Several collections inline their logo and banner as base64 (46KB for Astraea, 24KB for Karat G2); only `http(s)` images are kept, which is what takes the cached payload from ~94KB to ~4KB across all ten contracts. `banner_image` / `featured_image` are dropped entirely — nothing uses them yet.
  - **`background_color` is declared inconsistently and usually absent** — `#e9672b` on one collection, a bare `010813` on the next, and none at all on any Pistols contract or on Karat gen 1. `normalizeColor()` accepts both forms and drops anything else; `FOOLS` and `FAME` have no contract metadata at all, so a contract is simply absent from the map rather than present-and-empty. Never assume a colour is there.
  - **Which is why `contracts.json` carries `bgColor`** — the stock we want for a collection that ships no colour of its own (`Rings`, `Karat`). It rides through `PROFILE.tokens` as `TokenContract.bgColor` and `withFallbackColors()` fills it in wherever the chain's own `background_color` is missing; the contract's own value always wins. It is applied **on the way out of the provider, not folded into the cached payload**, because the `localStorage` cache is keyed on the address *set* — editing a colour in place invalidates nothing, so baking it in would leave the old stock on the felt for 24h. A contract Torii has no metadata row for gets no entry, hence no fallback either.
  - Torii returns both `metadata` and `token_metadata` on a contract row; which one carries the collection JSON isn't worth depending on, so `parseMeta` takes the first that parses to a non-empty object.
- `hooks/use-controller.ts` — the only thing components use for connection: `connect` / `disconnect` / `openController(tab)` / `username` / `address` / `isConnected`. Composes bare `@starknet-react/core` hooks; never wraps them in another cache.
- `preset: 'pistols'` gives the Controller the Pistols theme and its published policies. No `policies` of our own yet — those need a deployed world for *this* game.
- `@cartridge/controller/react`'s `ControllerToaster` (and its stylesheet) is deliberately **not** mounted: it's optional, and the one-stylesheet rule means importing package CSS needs a reason. Add it when transaction toasts are wanted.
- `ControllerOptions.tokens` is **not** set: in `0.13.x` its `Token` type is a fixed union (`eth`/`strk`/`lords`/`usdc`/`usdt`), not arbitrary addresses, so the game's tokens can't be listed in the Controller inventory that way. `toriiUrl` is what surfaces them.

## Torii indexer (`torii/`)

**Everything about the indexer lives in [`torii/CLAUDE.md`](./torii/CLAUDE.md)** — read it before
touching `torii/`, the generated TOML, or the indexing side of `contracts.json`. Operational steps are
in `torii/README.md`; `torii/SPECS.md` is frozen history the implementation deliberately deviates from.

Two things that reach outside `torii/` and so belong here:

- **`contracts.json` at the repo root is the single source of truth** for which contracts Torii indexes *and* which tokens the client sees (`PROFILE.tokens`). One file, two consumers — a change to it is a change to both.
- **Torii never indexes backwards.** `indexing.world_block` (the oldest enabled `block`) is only a fallback for contracts with **no row in the db yet**; an already-indexed contract resumes from its stored `head`. So adding an *older* contract costs the existing index nothing and backfills itself fine — but **re-indexing an existing contract from an earlier block, or dropping one, requires wiping data**, and `enabled: false` alone does not stop indexing it. Warn about that *before* editing `contracts.json`, offer both wipe options, never wipe unasked. Full mechanism, source citations and the live-db check: `torii/CLAUDE.md`.
